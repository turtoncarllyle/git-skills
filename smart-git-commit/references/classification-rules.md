# 智能分类规则

在智能模式中使用本文件。目标是产生按技术层和业务模块划分、可独立审阅的提交，而不是按文件扩展名机械聚合。

## 1. 理解仓库结构

先读取仓库已有约定和入口文件，例如 `AGENTS.md`、解决方案或工作区文件、项目清单、包管理清单以及现有目录结构。只读取与分类有关的内容，不运行有副作用的构建、迁移或生成命令。

优先使用以下证据判断文件归属：

1. 明确的 feature、domain 或 module 目录。
2. 命名空间、包名、路由、控制器和组件引用关系。
3. 项目文件、workspace 或 monorepo 配置。
4. 文件扩展名和常见目录名。

扩展名只能作为辅助证据。例如 `.cshtml` 可能同时包含服务端 Razor 和前端资源，`Views` 目录也可能属于后端 MVC 项目。

## 2. 确定技术层

| 层级 | 常见证据 | 处理方式 |
| --- | --- | --- |
| 公共契约 | `contracts`、`shared`、DTO、schema、公共类型 | 独立成组并优先提交 |
| 后端 | `api`、`server`、`backend`、Controller、Service、Domain、Repository | 按业务模块分组 |
| 前端 | `client`、`frontend`、`web`、页面、组件、状态管理、样式资源 | 按业务模块分组 |
| 配置 | 项目配置、构建配置、依赖清单、锁文件、CI 文件 | 与业务实现分离 |
| 文档 | Markdown、说明、示例文档 | 按同一文档目的分组并最后提交 |

数据库迁移、数据模型和对应后端实现存在不可分割关系时，将迁移归入对应后端模块。跨层共享 schema 或生成源文件归入公共契约，不把生成结果与无关业务文件合并。

## 3. 推断业务模块

从离文件最近且具有业务语义的目录、命名空间、路由或类型推断模块，例如认证、用户、订单、支付、报表。忽略 `src`、`app`、`components`、`services`、`tests` 等纯技术容器名称。

无法从路径确认时，读取文件内容和引用关系。仍无法判断时使用具体且中性的模块名，例如“公共组件”或“基础设施”，不要猜测业务含义。

## 4. 确定修改目的

在同一层级和模块内继续按主要目的拆分：

- 新增可观察能力：`feat`
- 修复错误行为：`fix`
- 行为不变的结构调整：`refactor`
- 可验证的性能改进：`perf`
- 仅格式变化：`style`
- 仅测试变化：`test`
- 仅文档变化：`docs`
- 配置、构建或维护：`chore`

不要只根据文件是新增还是修改来选择类型。一个新增测试文件可能属于 `fix` 组，一个修改现有文件也可能实现 `feat`。

## 5. 形成提交组

以“技术层 + 业务模块 + 修改目的”为主要分组键，并应用以下约束：

- 前端与后端永远分开。
- 不同业务模块分开。
- 同一模块中的实现和直接验证该实现的测试放在一起。
- 仅测试变更单独使用 `test`。
- 配置文件不与业务实现混合；同一依赖的清单文件和锁文件可以同组。
- 文档不与代码混合；描述同一变更的一组中英文文档可以同组。
- 多个文件只有在共同构成一个可说明、可审阅的变化时才能同组。
- 一个提交组过大或包含多个目的时继续拆分。

若严格分层会让中间提交不可理解，优先提交公共契约，再提交后端，最后提交前端，使后续提交建立在前置契约之上。

## 6. 排序

默认按以下依赖顺序输出计划：

1. 公共契约、schema 或基础结构。
2. 后端业务模块。
3. 前端业务模块。
4. 独立配置和构建维护。
5. 文档。

同一层内按依赖关系排序；没有依赖时按模块名稳定排序。计划修改或跳过条目后重新计算依赖顺序。

## 7. 特殊文件

- 重命名：将源路径和目标路径视为一个逻辑变化。
- 删除：根据被删除内容原有职责分类。
- 生成文件：与生成源同组；无法确认生成关系时单独列出并说明。
- 二进制：根据路径和相邻内容分类，不推断不可见语义。
- 敏感文件：暂停并要求确认，不自动加入计划。
- 单文件多目的：要求用户先拆分，不自动使用交互式 patch。
